# Backend API Reference — for Frontend Integration

This is the complete, current contract between this backend and any
frontend consuming it. Built by reading the actual route files, handlers,
services, and error classes directly — not from memory — so it reflects
exactly what the code does today, not what it's supposed to do.

---

## How industries actually hand this off (the real answer to "how do teams communicate this")

There's a spectrum, roughly in order of how mature/automated the setup is:

1. **Nothing formal — Slack + reading the code together.** Common at very
   early-stage startups with 1-2 backend and 1-2 frontend engineers who
   sit in the same standup. Works until the team grows past ~4-5 people or
   frontend/backend split across time zones — then it breaks down fast.

2. **A hand-maintained reference doc** (this document). Common at small-to-mid
   teams. Cheap to produce, but drifts from reality the moment someone
   changes an endpoint and forgets to update the doc — which is why this
   one was generated by reading the actual route/handler/error-class code
   directly rather than from a spec written separately.

3. **OpenAPI / Swagger spec** — the real industry standard once a team
   has more than a handful of engineers or multiple frontend clients (web
   + mobile). The backend either hand-writes an `openapi.yaml`/`.json`, or
   (better) auto-generates it from the same validation schemas already
   used at runtime — this codebase already uses Zod for request validation
   (see `middleware/validate.ts`), and libraries like `zod-to-openapi`
   generate an OpenAPI spec directly from those same Zod schemas, so the
   validation code and the documentation can never drift apart. The spec
   then powers:
   - **Swagger UI / Redoc** — an interactive, always-current doc site
   - **Auto-generated typed clients** — tools like `openapi-typescript` or
     `orval` generate a fully-typed TypeScript client (including React
     Query hooks) directly from the spec, so frontend engineers get
     autocomplete and compile-time errors instead of hand-typing `fetch`
     calls and guessing response shapes
   - **Contract testing** — CI can validate that responses actually match
     the documented shape, catching drift automatically

4. **A shared schema/contract package** — for teams using TypeScript on
   both ends (monorepo or a published `@company/api-types` package), the
   request/response types themselves are the contract, imported directly
   by both sides. tRPC takes this further and generates the client from
   the server's actual router definitions, so there's no separate spec to
   maintain at all — the types ARE the documentation, enforced by the
   compiler. This only works cleanly when frontend and backend are both
   TypeScript.

5. **Postman/Insomnia collections** — common alongside any of the above,
   less for documentation and more for manual testing/exploration during
   development. Some teams export these from an OpenAPI spec automatically
   rather than maintaining them separately.

**What I'd suggest for this codebase specifically**, given it already uses
Zod everywhere: introducing `zod-to-openapi` to auto-generate an OpenAPI
spec from the existing validation schemas would get you options 3 and 4
above with fairly little new code, and would prevent this document from
becoming stale the way hand-written docs always eventually do. Flagging as
a suggestion, not doing it unprompted — this document works fine as a
snapshot of the current contract in the meantime.

## Base setup

**Base URL:** `/api/v1` (mounted in `app.ts`; health check at `/health`, unauthenticated)

**Auth:** Bearer JWT in the `Authorization` header on every route except
`POST /auth/register`, `POST /auth/login`, and `POST /tools/audit` (the
public free-audit tool). Token is obtained from register/login and must be
sent as:
```
Authorization: Bearer <token>
```
Missing or invalid token → `401 UNAUTHORIZED`. Token expiry is configured
server-side (`config.jwt.expiresIn`) — frontend should catch 401s globally
and redirect to login; there's no refresh-token flow, just re-login.

**Error shape — every error, every endpoint, identical structure:**
```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "keyword: String must contain at least 1 character(s)"
  }
}
```
Status code always matches the error type. The full set of `code` values
that exist today (`utils/errors.ts`):

| code | status | thrown when |
|---|---|---|
| `VALIDATION_ERROR` | 400 | Zod schema failed, or a service-level business-rule check failed |
| `UNAUTHORIZED` | 401 | Missing/invalid/expired JWT, or wrong login credentials |
| `FORBIDDEN` | 403 | Authenticated, but not a member of the project's organization |
| `NOT_FOUND` | 404 | Resource doesn't exist (or you don't have access — same response either way, deliberately, so existence isn't leaked) |
| `CONFLICT` | 409 | Duplicate (e.g. keyword already exists, email already registered) |
| `RATE_LIMIT` | 429 | Defined but not currently thrown anywhere in the routes covered below |
| `INTERNAL_ERROR` | 500 | Anything unexpected — message is deliberately generic, real detail is server-side logs only |

**Pagination convention** — used consistently across every list endpoint
that has one (blogs, keywords, code changes, FAQs, TLDRs, optimizations):
query params `?page=1&limit=20` (limit capped at 100 server-side
regardless of what's requested), response includes the page/limit/total
alongside the array — exact key names noted per-endpoint below since they
vary slightly (e.g. `{ blogs, total, page, limit }` vs `{ keywords, total, page, limit }`).

**Route param convention:** almost everything is nested under a project —
`/projects/:projectId/<resource>`. `mergeParams: true` is set on every
sub-router so `:projectId` is available inside blog/keyword/cms/geo/gsc/
knowledge/audit/optimization handlers even though it's declared on the
parent router in `routes/api-v1/index.ts`, not the sub-router itself.

**Full mount map** (`routes/api-v1/index.ts`):
```
/auth                              → auth.route.ts       (public)
/projects                          → project.route.ts    (auth required)
/projects/:projectId/audit         → audit.route.ts
/projects/:projectId/blogs         → blog.route.ts
/projects/:projectId/keywords      → keyword.route.ts
/projects/:projectId/cms           → cms.route.ts
/projects/:projectId/geo           → geo.route.ts
/projects/:projectId/gsc           → gsc.route.ts
/projects/:projectId/knowledge     → knowledge.route.ts
/projects/:projectId/optimizations → optimization.route.ts
/tools                             → tools.route.ts       (public)
```

## Auth (`/auth`) — public, no token required

### `POST /auth/register`
**Why:** create a new user + their personal organization in one step (every
user gets an org even if solo — projects belong to orgs, not users
directly, so agency accounts work the same way from day one).

Request body:
```ts
{
  name: string;               // 1-100 chars
  email: string;               // valid email
  password: string;            // 8-100 chars
  accountType?: 'individual' | 'agency';  // default 'individual'
  utmSource?: string;
  utmMedium?: string;
  utmCampaign?: string;
}
```
Response `201`:
```ts
{
  token: string;               // JWT — store this, send as Bearer on everything else
  user: { id, name, email, accountType, organizationId };
}
```
Errors: `409 CONFLICT` if email already registered.

### `POST /auth/login`
Request: `{ email: string; password: string }`
Response `200`: identical shape to register's response.
Errors: `401 UNAUTHORIZED` for wrong email or password — **deliberately
the same message either way** ("Invalid email or password"), so a login
form can't be used to enumerate registered emails.

## Projects (`/projects`) — auth required on everything below

### `POST /projects`
**Why:** creates the project AND immediately kicks off the pipeline's first
two steps (site crawl → AI business-profile draft) in the background —
this is why project creation feels "instant" from the caller's side but
work continues after the response comes back (see `docs/02-phase2-business-profile-audit.md`
for the full pipeline-pause-for-onboarding design).

Request: `{ domain: string; keywordPrimaryCountryCode?: string }`
Response `201`: `{ project, ... }` — check `project.status`/pipeline-related
fields to know it's mid-crawl; poll `GET /:id/pipeline/status` (below) for
progress rather than assuming it's done.

### `GET /projects`
No params. Response `200`: `{ projects: [...] }` — every project the
user's organization has access to.

### `GET /projects/:projectId`
Response `200`: `{ project }`. `404` if it doesn't exist or you're not a
member of its organization (same response for both, see error table above).

### `GET /projects/:projectId/business`
**Why:** fetch the current onboarding/business-context state — used to
pre-fill the onboarding wizard and to check what the AI has drafted so
far. Response `200`: `{ businessContext }` — **can be `null`** if the
crawl/business-profile step hasn't completed yet; frontend must handle
that explicitly, it's not an error state.

Two separate progress fields worth knowing about on the returned object
(see `docs/02-phase2-business-profile-audit.md` for why these are split):
- `aiDraftedSteps: number[]` — which steps the AI has auto-filled but a
  human hasn't reviewed yet
- `completedSteps: number[]` — which steps a human has actually confirmed
  via the wizard

Use `completedSteps` to drive "is onboarding done" logic, not
`aiDraftedSteps` — the latter is UI-hint-only (e.g. "AI has a suggestion
for you here").

### `POST /projects/:projectId/onboarding/step`
**Why:** saves one wizard step at a time (5-step onboarding: Company,
Product, Customers, Competition, Social Proof), so users can leave and come
back without losing progress.

Request: `{ step: 1 | 2 | 3 | 4 | 5; data: { ...step-specific fields } }`

The `data` shape is intentionally untyped at the route level
(`z.record(z.unknown())`) — each step maps to a different section of
`BusinessContext`, so check `models/BusinessContext.ts` for the exact
field names per step. One field worth flagging specifically: **step 4's
`mainCompetitors` is submitted as a plain array of domain strings** — the
backend wraps each one server-side into a richer object
(`{domain, source: 'user', verified, verificationReasoning, addedAt}`,
see `docs/05-phase4-competitor-discovery-audit.md`) before storing and
before it comes back on later `GET` calls. **Submit plain strings, expect
objects back** — this is a real, easy-to-miss asymmetry.

Response `200`: the updated onboarding state.

### `POST /projects/:projectId/pipeline/start`
**Why:** explicit "I'm done with onboarding, go" trigger — resumes the
pipeline from where it paused after the initial AI draft (technical audit
→ competitor discovery → keyword research run automatically after this).

Request: `{ keywordPrimaryCountryCode?: string }`
Response `200`: pipeline resume result.

### `GET /:id/pipeline/status`
**Why:** poll this to drive a progress UI while the pipeline runs — note
the param is `:id` here, not `:projectId` (inconsistent with every other
project sub-route, called directly on the router not through a
`mergeParams` sub-router — worth knowing so it's not assumed to follow the
same pattern as everything else).
Response `200`: current step + status per step.

### `POST /:id/pipeline/resume`
**Why:** manually force-resume from a specific step — an admin/support
action more than a normal user action (see `docs/06-phase5-keyword-research-audit.md`
for a real edge case this can trigger if used carelessly against
`KEYWORD_RESEARCH` after content generation has already started).
Request: `{ fromStep?: string }`
Response `200`: resume result.

### `POST /projects/:projectId/business` (legacy, kept for backward compat)
Request: `{ domainDescription: string; oldDomainDescription: string; isDraft: boolean }`
Prefer the onboarding-step endpoint above for anything new — this exists
for whatever still calls it, not recommended for new frontend work.

## Blogs (`/projects/:projectId/blogs`)

### `GET /blogs?status=&page=&limit=`
Response `200`: `{ blogs: [...], total, page, limit }`.
`status` filter is optional — one of the `Blog.status` enum values
(`draft`, `ready`, `published`, `archived`).

### `GET /blogs/:blogId`
Response `200`: `{ blog }`.

### `PATCH /blogs/:blogId`
**Why:** manual edits to a blog before/after publish.
Request (all optional): `{ title?, content?, description?, status? }`
— `status` here is direct manual override, distinct from the
publish/unpublish endpoints below which also update CMS state, not just
the DB record.
Response `200`: `{ blog }`.

### `POST /blogs/:blogId/publish`
**Why:** push to the connected CMS. Response `200`:
`{ blog, message: 'Publish job enqueued' }` — **note this returns before
the actual CMS push completes** (enqueued, not synchronous) despite
returning `200` — poll `GET /blogs/:blogId` and check `blog.status`/
`blog.publishedUrl`/`blog.cmsReference` to know when it's actually live,
don't treat the `200` as "it's published now." Idempotent — calling this
on an already-published blog is a safe no-op (see `docs/11-cms-integrations-audit.md`).

### `POST /blogs/:blogId/unpublish`
Response `200`: `{ blog }`.

### `DELETE /blogs/:blogId`
Response `200`: `{ blog }` (the deleted document, for confirmation UI).

## Keywords (`/projects/:projectId/keywords`)

### `GET /keywords?status=&weekNumber=&page=&limit=`
Response `200`: `{ keywords: [...], total, page, limit }`.
`weekNumber` filters to one content-calendar week (see
`docs/12-weekly-generation-scheduling.md` for how weeks are scheduled).

Fields worth knowing about on each keyword object (`models/Keyword.ts`
has the full doc-commented list): `status` (`upcoming → generating →
draft → ready → published`), `source` (`ai_suggested | user_added |
gsc_import | dataforseo`), `searchVolume`/`difficulty`/`cpc`,
`alignmentScore`/`relevanceReason`, and `suggestedTitle` — a preview title
generated at discovery time, **may differ from the actual `Blog.title`**
once content is generated; use it for a "coming soon" preview only, not
as a promise of the final title.

### `POST /keywords`
**Why:** user manually adds a keyword outside the automated pipeline —
runs real-time verification (search volume + business relevance) before
accepting, see `docs/14-manual-keyword-verification.md` for the full
rule. Request: `{ keyword: string }`.
Response `201`: `{ keyword }` — same shape as list items, with real
`searchVolume`/`alignmentScore`/`relevanceReason` populated (not
placeholder values).
Errors: `409 CONFLICT` if the keyword already exists for this project;
`400 VALIDATION_ERROR` **only** if the keyword shows both zero search
volume AND is judged irrelevant to the business — a low-but-nonzero
volume or an unclear relevance judgment is never enough alone to reject.
This call can take a few seconds (real API calls happen synchronously
before responding) — show a loading state, don't assume it's instant like
most other POSTs.

### `DELETE /keywords/:keywordId`
Response `200`: `{ keyword }`.

### `POST /keywords/:keywordId/generate`
**Why:** manually trigger content generation for one keyword (most
keywords generate automatically on their scheduled week — see
`docs/12-weekly-generation-scheduling.md` — this is the "do it now
instead of waiting" button).
Response `202` (Accepted, not 200 — this is enqueued work):
`{ status: 'generating', keywordId }`. Poll `GET /keywords` or
`GET /blogs` to see the result land. Errors `400 VALIDATION_ERROR` if the
keyword isn't in `upcoming` status (already generating or done).

## CMS connection (`/projects/:projectId/cms`)

### `GET /cms`
Response `200`: `{ cmsConfig }` — **can be `null`** if nothing's connected yet.

### `POST /cms/connect`
**Why:** connect a CMS platform. Request:
```ts
{
  cmsType: string;   // 'wordpress' | 'webflow' | 'wix' | 'shopify' | 'sanity' | 'gohighlevel' | 'framer' | 'squarespace' | 'custom_api' | 'other'
  credentials: Record<string, unknown>;  // shape is cmsType-specific — see lib/cms/types.ts per platform
  blogPostPath?: string;
}
```
Response `200`: `{ cmsConfig }`. Credentials are encrypted at rest —
never returned back in any response, including this one.

**Worth surfacing in the UI if `cmsType` is `'framer'`**: this platform
has a real, unresolved backend issue right now (see
`docs/11-cms-integrations-audit.md`, 🔴 critical finding) — publishing
will not actually work correctly. Not a reason to block the connect call
itself, but worth a warning in the UI until that's fixed.

### `PATCH /cms`
Request (all optional): `{ autoPublish?: boolean; allowedPublishDays?: number[]; blogPostPath?: string }`
— `allowedPublishDays` is 1-6 (Mon-Sat), matching `Date.getUTCDay()`.
**Turning `autoPublish` on is what actually starts the recurring publish
schedule** (see `docs/07-phases6-8-content-generation-publish-audit.md`)
— connecting a CMS alone does not auto-publish anything.
Response `200`: `{ cmsConfig }`.

### `DELETE /cms/disconnect`
Response `200`: `{ message: 'CMS disconnected' }`. Also stops any
recurring publish schedule for the project.

## Knowledge base / RAG uploads (`/projects/:projectId/knowledge`)

### `GET /knowledge`
Response `200`: `{ files: [...] }`.

### `POST /knowledge`
**Why:** upload a brand document (pricing sheet, case study, brand
guide) that gets chunked + embedded for retrieval during blog generation
— see `docs/13-knowledge-learning-system.md` for the full RAG pipeline.
**`multipart/form-data`, not JSON** — field name must be exactly `file`.
10MB hard limit (enforced at the multer layer, before it reaches any
handler code — an oversized file gets rejected before your validation
logic even runs). Supported formats today: pdf, txt, md, csv, json —
**not docx** (deferred, see `docs/13-...`).
Response `201`: `{ file }` — starts as `status: 'pending'`, moves through
processing asynchronously; poll `GET /knowledge` to see it reach `ready`.

### `DELETE /knowledge/:fileId`
Response `200`: `{ file }`. Also cleans up the file's embedded chunks
(fixed as part of this RAG build — previously deleting a file left its
chunks orphaned in search results forever).

## Technical audit (`/projects/:projectId/audit`) — read + limited write

### `GET /audit`
Response `200`: `{ audit }` — the latest technical SEO audit (see
`docs/04-phase3-technical-audit-audit.md`), includes the overall score and
summary. `404 NOT_FOUND` if no audit has fully completed yet (crawl and
fix-generation both need to finish) — treat this like the `businessContext:
null` case elsewhere: not an error state, just "still working," and show
a loading UI rather than an error message.

### `GET /audit/code-changes?type=&status=&page=&limit=`
Response `200`: `{ codeChanges: [...], total, page, limit, auditReady: boolean }`.

**`auditReady` is the key field to check before rendering anything here.**
`site-crawl.job.ts` creates these records immediately, but the actual
before/after HTML (`oldHtml`/`newHtml`) gets filled in by the *next*
pipeline step afterward — so calling this while that's still running
would previously return partially-generated records (empty `newHtml`,
looking broken in the UI). Now: `auditReady: false` + an empty
`codeChanges` array means "still generating, show a loading/working
state"; `auditReady: true` means everything for this audit run is fully
populated and safe to render all at once, matching how RankAI's own UI
only ever shows fully-formed fix cards. Poll this endpoint (or `GET
/audit` for its `404`/`200` state) until `auditReady` flips to `true`
rather than rendering incrementally.

Each `codeChange` has real `oldHtml`/`newHtml` markup — display them
directly, matching RankAI's "NEW"/"PREVIOUS" pattern. When nothing existed
before the fix, `oldHtml` is now a friendly placeholder string (e.g. `"No
Open Graph tags found"`, `"No canonical tag found"`, `"No schema markup
found"`, `"No meta description found"`) rather than an empty string — no
frontend fallback logic needed for that case, just render `oldHtml` as-is.

### `POST /audit/code-changes/:changeId/apply`
Response `200`: `{ codeChange }` — marks a suggested fix as applied.

### `POST /audit/code-changes/:changeId/disable`
Response `200`: `{ codeChange }` — dismiss a suggested fix without applying it.

### `GET /audit/faqs?status=&page=&limit=`
Response `200`: `{ faqs: [...], total, page, limit, auditReady: boolean }` —
same `auditReady` gating as code-changes above. Scoped to the latest
completed audit run specifically (`FAQ` now has a real `auditId` field,
same as `CodeChange`) — results from an earlier audit run never mix in
with the current one, even across re-crawls.

### `GET /audit/tldrs?status=&page=&limit=`
Response `200`: `{ tldrs: [...], total, page, limit, auditReady: boolean }` —
same `auditReady` gating and audit-scoping as FAQs above.

## Content optimization review queue (`/projects/:projectId/optimizations`)

**Why this whole resource exists:** the closed-loop learning system
(`docs/13-knowledge-learning-system.md`) watches GSC performance on
published blogs and proposes fixes. Tag/metadata changes auto-apply with
a rollback safety net; full content rewrites land here for a human to
approve or reject before anything changes.

**Access note:** currently any project member can approve/reject — not
restricted to owner/admin (a deliberate, flagged-for-later choice, not an
oversight — see `services/optimization.service.ts`'s doc comment if this
ever needs tightening).

### `GET /optimizations?status=&blogId=&page=&limit=`
Response `200`: `{ optimizations: [...], total, page, limit }`.
`status` defaults to `pending_review` if not specified — i.e. calling this
with no query params gives you the actual review queue, not full history;
pass `status=applied` or `status=rejected` explicitly to see past decisions.

### `GET /optimizations/:optimizationId`
Response `200`: `{ optimization }` — includes both the original and
proposed content/tags side by side for a diff-style review UI.

### `PATCH /optimizations/:optimizationId/approve`
**Why:** applies the proposed content rewrite to the live `Blog` document
AND pushes it to the connected CMS if already published (see
`lib/blog-cms-publisher.ts`'s `updateBlogOnCms`) — works for 6 of 8 CMS
platforms; Framer is excluded (see the CMS section above). If the CMS
push fails, it's automatically retried every 4 hours server-side — the
frontend doesn't need to build its own retry logic, just know that
"approved" doesn't always mean "live on the CMS within the same request."
Response `200`: `{ optimization, message: 'Optimization applied' }`.
Errors: `400 VALIDATION_ERROR` if already approved/rejected, or if this
particular optimization has no content proposal (tag-only optimizations
auto-apply already — there's nothing for this endpoint to do for those).

### `PATCH /optimizations/:optimizationId/reject`
Response `200`: `{ optimization, message: 'Optimization rejected' }`.

## Things every frontend integration should get right from day one

1. **Every list endpoint uses the same pagination shape** — build one
   shared hook/utility for it rather than re-implementing per-resource.
2. **`404` means either "doesn't exist" or "you don't have access"** —
   never build UI copy that says "not found" when it might actually be a
   permissions issue; use generic "couldn't load this" messaging.
3. **Several endpoints return `200`/`201`/`202` before the real work is
   done** (blog publish, keyword generate, knowledge upload) — anywhere
   this doc says "enqueued" or "poll for status," build the polling UI
   from the start rather than assuming the response means completion.
4. **The onboarding step-4 competitor field is submit-string/receive-object**
   — the one asymmetric field shape in the whole API, called out
   explicitly above because it's the one most likely to cause a silent
   bug if missed.
5. **Auth errors are indistinguishable by design in a couple of places**
   (wrong email vs wrong password; resource missing vs no access) — don't
   fight this in the UI, it's intentional.
